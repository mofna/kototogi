# 技術文書の書き換え例

架空の実装と検証メモから作った校正例です。数値は説明用の設定です。原稿と材料を読み、kototogiの方針で段落を整えています。

## CSV取込みのメモリー使用量を減らす

### 材料

取込ツールの旧実装は`csv.DictReader`の結果を全件リストにしてからDBへ渡していました。改修後は読みながら1,000件ずつ書込みを確定し、末尾の端数も書き込みます。

同じ30万件を同じ検証環境で改修前後に4回ずつ取り込んだ設定です。各回の最大メモリー使用量の中央値は512 MiBから96 MiBへ減りました。必須項目が空ならレコード番号を出して停止し、確定済みの分だけDBに残ります。4,312件目に不備のある入力では先頭4,000件が保存されました。再開位置を指定するオプションは追加予定です。

### 校正前

````markdown
30万件のCSVを読み込ませたら、取込中のメモリー使用量が気になった。小さいファイルなら平気だったので、つい後回しにしていたんだよね。実装を見たところ、`csv.DictReader`の結果を全部リストにしてからDBへ渡していた。ここで重要なのは、単なる読込み処理の置き換えではなく、メモリーに保持する件数を見直すことだ。

そこで、読みながら、1,000件ずつDBへ書き込んで確定し、端数も最後に書き込む形へ変えた。これが地味に効いた。同じ30万件を同じ検証環境で4回ずつ取り込み、各回の最大メモリー使用量の中央値は512 MiBから96 MiBへ減った。この数値はこの環境での測定結果であり、すべての環境の結果ではない。

必須項目が空だったときはレコード番号を出して停止する。確定済みの分はDBに残り、処理中の分は書き込まない。検証では4,312件目のエラーで停止し、先頭の4,000件が残った。次はこの番号を手掛かりに、再開位置を指定するオプションを追加する予定だ。これは実装済みという意味ではない。
````

### 校正後

````markdown
30万件のCSVを読み込ませたら、取込中のメモリー使用量が気になった。小さいファイルなら平気だったので、つい後回しにしていたんだよね。

`csv.DictReader`の結果を全部リストにするのをやめ、読みながら1,000件ずつDBへ書き込んで確定する形に変えた。端数も最後に書き込む。同じ30万件を同じ検証環境で4回ずつ取り込むと、各回の最大メモリー使用量の中央値は512 MiBから96 MiBへ減った。

必須項目が空ならレコード番号を出して停止する。確定済みの分はDBに残り、処理中の分は書き込まない。検証では4,312件目のエラーで停止し、先頭の4,000件が残った。次はこの番号を手掛かりに、再開位置を指定するオプションを追加する予定だ。
````

### 編集したところ

背景、変更と測定結果、失敗時の処理と次の予定という順に整理しました。作用の曖昧な評価は後続の測定結果で説明できます。環境や予定の言い直しは省き、未確定のレコードを扱う否定文は処理の説明として残しました。

## 検索APIのページ送りを変える

### 材料

架空の記事検索画面は新着順に50件ずつ表示し、「次へ」で読み進めます。`published_at`は公開日時、`id`は一意な識別子です。両列は`NOT NULL`で登録後に変更しない仕様です。改修前は`OFFSET`を使い、先頭へ記事を追加すると前ページ末尾の既出記事が次ページにも現れました。

改修後は`published_at`と`id`の降順でページを区切ります。同じ公開日時の記事8件が境界をまたぐ入力を使い、先頭への追加後も既出記事を重複なく取得した設定です。公開日時の編集機能は検討中です。

SQLの行比較と`LIMIT`の意味は末尾のPostgreSQL資料に対応します。`$1`と`$2`はカーソルの値を渡すパラメーターです。

### 校正前

````markdown
記事検索APIでは、新着順で50件ずつ表示している。これまでは`OFFSET`で読飛ばす件数を指定していたが、閲覧中に先頭へ記事が追加されると、前ページの末尾が次ページにも出ることがあった。画面は「次へ」で読み進められればよいので、カーソル方式へ変更することにした。

ここで重要なのは、単に公開日時だけを保存するのではなく、同じ公開日時の記事も含めて順序を決めるということだ。`published_at`の降順に並べ、同値なら一意な`id`の降順にする。両列は`NOT NULL`で登録後に変更しない。次のカーソルには前ページの最後の`published_at`と`id`を入れる。

次ページのSQLは以下になる。`$1`はカーソルの公開日時、`$2`はIDを表す。先頭ページは`WHERE`条件を省く。[S1][S2]

```sql
SELECT id, published_at, title
FROM articles
WHERE (published_at, id) < ($1, $2)
ORDER BY published_at DESC, id DESC
LIMIT 50;
```

検証では同じ公開日時を持つ8件がページ境界をまたぐ入力を使い、先頭への記事追加後も既出記事を重複なく取得できた。ただし、これは並び替えに使う値を固定した条件での検証だ。公開日時を編集できるようにする案は検討中であり、現在の仕様とは分けて考える必要がある。
````

### 校正後

````markdown
記事検索APIでは新着順で50件ずつ表示している。`OFFSET`で読飛ばす件数を指定していたときは、閲覧中に先頭へ記事が追加されると前ページの末尾が次ページにも出ることがあった。画面は「次へ」で読み進められればよいので、カーソル方式へ変更することにした。

`published_at`の降順に並べ、同値なら一意な`id`の降順にする。両列は`NOT NULL`で登録後に変更しない。次のカーソルには前ページの最後の`published_at`と`id`を入れる。公開日時を編集できるようにする案は検討中だ。

次ページはカーソルの組より小さい値を持つ行を取得する。SQLの`$1`はカーソルの公開日時、`$2`はIDを表す。先頭ページは`WHERE`条件を省く。[S1][S2]

```sql
SELECT id, published_at, title
FROM articles
WHERE (published_at, id) < ($1, $2)
ORDER BY published_at DESC, id DESC
LIMIT 50;
```

同じ公開日時を持つ8件がページ境界をまたぐ入力で確認したところ、先頭への記事追加後も既出記事を重複なく取得できた。
````

### 編集したところ

日時だけで順序を決めることへの注意を、並び順とカーソルの仕様にまとめました。検討中の案は現在の仕様の隣へ移しています。SQLとパラメーターの説明を保ち、最後は実際に確認した入力と結果で終えました。

公開日時の固定という条件と、編集機能を検討している状態は両方必要です。これらを省くと設計上の選択が読み取れなくなります。
