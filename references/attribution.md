# 情報の種類と出典

出典名を本文に置くかは、その情報の役割で決める。仕様や一般的な動作は対象を主語にし、根拠のリンクや参照番号を添える。

| 情報 | 書き方 |
|---|---|
| 仕様・構文・一般的な動作 | 対象を主語にして説明する |
| 個別の測定・調査結果 | 報告元と条件を示す |
| 選んだ資料の手順・推奨 | 紹介元や推奨した主体を示す |
| 見解・未確定の報告・直接引用 | 発信元と主張の確かさを保つ |

媒体の名前より文が伝える内容を見る。仕様の適用に必要な版や環境も本文へ添える。

## 分割アップロードを説明する例

以下は架空のAPIを使った作例。参照番号は次の仕様書・ガイド・比較記録を示す。各資料の内容と測定値は説明用に設定している。

### 材料

[S1] 仕様書：ファイルを8 MiBずつ分割して受け付ける。送信先は`upload_id`と`part_no`で指定し、同じ組への再送は同じ部分を上書きする。登録済みのpart番号を一覧取得できる。`complete`は全partの受信後に実行し、不足があれば`409`を返す。

[S2] 導入ガイド：中断後は登録済みのpart番号を取得し、未登録のpartだけ送信する。最後に`complete`を呼ぶ再開手順を紹介している。

[S3] 基盤チームの比較記録：同じ800 MiBのファイルを改修前後に10回ずつ送信し、毎回400 MiBの受信後に通信を切断した。再接続から完了までの時間の中央値は、全体を再送する方式で73秒、未登録のpartだけ送る方式で28秒だった。

### 校正前

````markdown
800 MiBの動画を送るとき、通信が切れるたびに最初から送り直すのが気になっていました。公式仕様書によると、このAPIはファイルを8 MiBずつ分割して受け付けます。仕様書の説明によると、`upload_id`と`part_no`の組が同じ送信は同じ部分を上書きします。[S1]

導入ガイドでは、中断したアップロードを次の手順で再開する方法を紹介しています。[S2]

1. 登録済みのpart番号を取得します。
2. 未登録のpartだけ送信します。
3. `complete`を呼んで全体を確定します。

ここで注意したいのは、`complete`は全partの受信後に実行するという点です。不足があれば`409`が返ります。[S1]

基盤チームの比較記録では同じ800 MiBのファイルを改修前後に10回ずつ送り、毎回400 MiBの受信後に通信を切断しました。再接続から完了までの時間の中央値は、全体を再送する方式の73秒から、未登録のpartだけ送る方式の28秒へ減っています。これは筆者が再実行した結果ではありません。[S3]
````

### 編集したところ

最初の段落は仕様を直接説明し、参照番号を残した。再開手順は導入ガイドの紹介として続け、測定結果には基盤チームと比較条件を示している。

最後の段落は冒頭で報告元が分かるため、筆者の未実施を断る文を省いた。短くなった時間が「再接続から完了まで」である点も維持している。手順とエラー応答は同じ内容で読める。

## 点検の判断

S10は資料名付きの説明文を再読候補として示す。資料と前後を読み、出典名が情報を加えるか確かめる。S08で筆者の断りを削るときも同じ基準を使う。

段落の冒頭で帰属が伝われば内容を続ける。出典名を省いた後は参照の位置と適用条件を確認する。
